Beyond the `modmap` and `keymap` sections, xremap recognises several top-level keys that tune its global runtime behaviour. All options are optional — leaving them out is equivalent to accepting the documented default. They can be placed anywhere at the top level of your config file, though placing them before `modmap` and `keymap` is conventional.

```yaml
# Example showing all global options at once
virtual_modifiers:
  - CapsLock
keypress_delay_ms: 10
throttle_ms: 10
default_mode: default
notifications: false
config_watch_debounce_ms: 20
enable_wheel: true
shared:
  my_anchor: &my_anchor
    - value1
    - value2
```

---

## `virtual_modifiers`

<ParamField path="virtual_modifiers" type="string[]" default="[]">
  A list of key names that should be treated as modifier keys. This lets you use any ordinary key as if it were Ctrl, Alt, or Shift in `keymap` combo syntax.
</ParamField>

By default, only the hardware modifier keys (Ctrl, Alt, Shift, Super, etc.) can be used as the left-hand side of `-` in a combo like `Ctrl-N`. With `virtual_modifiers` you can promote any key to modifier status and write combos like `CapsLock-i`:

```yaml
virtual_modifiers:
  - CapsLock

keymap:
  - remap:
      CapsLock-i: Up
      CapsLock-j: Left
      CapsLock-k: Down
      CapsLock-l: Right
```

<Note>
  `virtual_modifiers` is merged across multiple config files, just like `modmap` and `keymap`. If you split your configuration across files, you can declare virtual modifiers in any of them.
</Note>

## `keypress_delay_ms`

<ParamField path="keypress_delay_ms" type="integer" default="0">
  Delay in milliseconds inserted between synthetic key events generated by `keymap` combos. Useful when applications fail to register events generated at full speed.
</ParamField>

Some applications — especially on Wayland — cannot keep up with key events synthesised at machine speed. Increasing this value gives each application time to process a press before the next event arrives:

```yaml
keypress_delay_ms: 10
```

<Tip>
  Start with a small value like `10` and increase it only if you still see dropped events. If `keypress_delay_ms` alone is insufficient, try `throttle_ms` which affects a broader set of events.
</Tip>

Only events produced by key combos in `keymap` are delayed. Passthrough keys (ones that do not match any rule) are not affected.

## `throttle_ms`

<ParamField path="throttle_ms" type="integer" default="0" >
  Slow down **all** synthetic events emitted by xremap, not just those from keymap combos. Available since v0.14.14.
</ParamField>

```yaml
throttle_ms: 10
```

The delay is applied between the following pairs of events:

- Press and release of the **same** key (but not in the reverse direction).
- Press of an ordinary key and a subsequent press or release of a modifier key.
- Press or release of a modifier key and a subsequent press of an ordinary key.

The logic is designed to give applications enough time to see the correct set of modifiers before the main key arrives, and to keep keys pressed long enough to be registered. The delay is only added when needed — if the required time has already elapsed, no extra wait is inserted.

<Note>
  `throttle_ms` affects a wider range of events than `keypress_delay_ms`. Prefer `keypress_delay_ms` for targeted fixes and reach for `throttle_ms` only when the former is insufficient.
</Note>

## `default_mode`

<ParamField path="default_mode" type="string" default='"default"'>
  The mode xremap starts in. If absent, xremap starts in a mode named `"default"`.
</ParamField>

```yaml
default_mode: Up_And_Down
```

Modes let you enable or disable groups of remappings at runtime. See the [Modes](/configuration/modes) page for a complete explanation and examples.

## `notifications`

<ParamField path="notifications" type="boolean" default="false">
  When `true`, xremap shows desktop notifications when it loads a configuration, reloads a configuration, or fails to reload a configuration. Available since v0.15.1.
</ParamField>

```yaml
notifications: true
```

<Note>
  The key `notifications` is misspelled as `notififactions` (with an extra `fi`) in xremap's own reference documentation. The actual YAML key accepted by xremap is `notifications` (the correctly-spelled version), which is derived directly from the Rust struct field name. Use `notifications` in your config.
</Note>

Notifications are sent via the standard desktop notification D-Bus interface and will appear in whatever notification daemon your desktop environment provides.

## `config_watch_debounce_ms`

<ParamField path="config_watch_debounce_ms" type="integer" default="0">
  Debounce delay in milliseconds for the `--watch=config` file watcher. Available since v0.15.1.
</ParamField>

```yaml
config_watch_debounce_ms: 20
```

When `--watch=config` is active, many text editors write config files in multiple steps (write to temp file → rename) which generates several filesystem events in quick succession. Without debouncing, xremap may attempt to reload a partially-written file and fail.

Setting a debounce delay causes xremap to wait for `config_watch_debounce_ms` milliseconds of file-system inactivity before reloading. Only the final event in a burst is acted upon.

```bash
xremap --watch=config config.yml
```

## `enable_wheel`

<ParamField path="enable_wheel" type="boolean" default="true">
  Controls whether the virtual output device created by xremap advertises support for `REL_HWHEEL` and `REL_WHEEL` mouse scroll events.
</ParamField>

```yaml
enable_wheel: false
```

By default, the xremap output device declares support for `REL_X`, `REL_Y`, `REL_HWHEEL`, and `REL_WHEEL`. This is usually harmless, but some desktop environments or applications behave differently when a device claims to support scroll events. Setting `enable_wheel: false` removes `REL_HWHEEL` and `REL_WHEEL` from the output device's capabilities.

<Note>
  This option only affects what the **output** device advertises. It does not change which input devices xremap listens to. To listen to mouse devices as input, use the `--mouse` command-line flag.
</Note>

## `shared`

<ParamField path="shared" type="any">
  An arbitrary data field that xremap ignores entirely at runtime. Intended as a scratch area for YAML anchors and aliases so you can reuse values across the config without repetition.
</ParamField>

```yaml
shared:
  terminals: &terminals
    - Gnome-terminal
    - Kitty
    - Alacritty

  emacs_bindings: &emacs_bindings
    Ctrl-f: Right
    Ctrl-b: Left
    Ctrl-n: Down
    Ctrl-p: Up

keymap:
  - application:
      only: *terminals      # Reuse the terminal list
    remap: *emacs_bindings  # Reuse the binding map
```

The `shared` field is evaluated by the YAML parser before xremap reads the config, so anchors defined inside it can be referenced anywhere else in the same file. xremap itself never reads the value of `shared`.

For more information on YAML anchors and aliases see the [YAML specification §3.2.2.2](https://yaml.org/spec/1.2.2/#3222-anchors-and-aliases).
